Beyond CPU Utilization: Choosing the Right Metrics for EC2 Auto Scaling

When configuring an EC2 Auto Scaling Group (ASG), CPU utilization is usually the first metric we reach for. A target tracking policy keeps average CPU near 60%: above it, the ASG launches instances; below it, it terminates the ones it doesn’t need.

That works for many workloads. But what if CPU is only 20%, yet your application is struggling to serve requests? CPU is only one signal. Memory, network, incoming requests or pending jobs can become the bottleneck long before CPU moves.

1. CPU utilization: when it makes sense

Two instances behind an Application Load Balancer run CPU-heavy work: image processing, calculations, report generation. As load grows, CPU grows with it. With a 60% target and 85% current average on 2 instances, target tracking estimates the capacity it needs as 2 × 85 ÷ 60 ≈ 2.8, so it scales to 3 instances.

Use CPU when CPU consumption closely tracks application demand.

2. ALB request count per target: scale on traffic

Picture an e-commerce site during a big sale. CPU may look fine while each instance already receives more requests than it can serve comfortably. The predefined metric ALBRequestCountPerTarget measures the average requests per target per minute, so you scale on demand instead of waiting for CPU.

Best for web apps, REST APIs and anything behind an ALB. Choose the target from load testing: find the request rate at which latency starts to degrade, then leave headroom.

3. Memory utilization: when RAM is the bottleneck

A Java service holds data in memory. CPU is 25%, memory is 90%. A CPU-only policy sees plenty of room, while GC pressure and OOM errors loom. EC2 does not publish memory to CloudWatch by default, so install the CloudWatch Agent and use the custom metric (for example mem_used_percent) in a target tracking policy.

Two caveats worth knowing: a JVM often holds its heap near the configured maximum even when idle, so raw memory % can look high without real pressure. Target tracking also works best when the metric falls as instances are added, so use an average across the group, not a sum.

4. Queue depth: scale on pending work

Workers consume order emails, invoices, payments and reports from an SQS queue. Two workers, 2,000 waiting messages, low CPU, and a backlog that keeps growing. Scale on backlog per instance: ApproximateNumberOfMessagesVisible ÷ running instances, published as a custom metric.

A better way to pick the target than guessing “50 messages”: target = acceptable latency ÷ average processing time. If a message takes 0.5 s and you can tolerate 25 s of wait, the target is 50 per worker.

5. Network throughput: when data transfer is the limit

For streaming or large downloads, CPU may sit at 30% while bandwidth saturates and response time rises. Predefined metrics ASGAverageNetworkIn and ASGAverageNetworkOut report average bytes per instance. Set the target from your instance type’s bandwidth, for example about 60–70% of its baseline. Network volume alone isn’t proof of saturation, so pick the direction that actually limits you (in or out).

6. Combining multiple policies

You can attach several target tracking policies at once. Any policy can trigger scale-out, and the ASG follows the one that asks for the most capacity. Scale-in is conservative: it happens only when all policies with scale-in enabled agree capacity can shrink.

Conclusion

Auto Scaling isn’t just watching CPU and launching instances. It’s keeping enough capacity for changing workloads. Understand your bottleneck, pick a metric that represents real demand, and you’ll get a more responsive and cost-efficient architecture.

Don’t scale just because CPU is high. Scale on what your application actually needs.
